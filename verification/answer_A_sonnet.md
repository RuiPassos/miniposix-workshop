# Answer A — Claude Sonnet (separate conversation, no tools)

(1) read() returns 0 (EOF) once the pipe buffer is empty and no write ends remain open. Any data already in the pipe is still returned first, in order, and read() returns 0 only after it is drained. While data remains, read() returns up to the requested count, so partial reads are normal.

(2) No. EOF depends on all write-end descriptors being closed, not just the original one. dup(), dup2(), fcntl(F_DUPFD) and fork() all create new descriptors that refer to the same open file description (the same pipe write end). The kernel reports EOF only when every descriptor referring to the write end has been closed in every process. If another copy stays open, such as the dup'd fd or the child's inherited fd, then read() on an empty pipe blocks. With O_NONBLOCK it fails with -1 and errno EAGAIN. It does not return 0. This is the classic bug where a parent forgets to close its unused write end and the reader hangs forever. The same holds for processes started with exec if the fd is not close-on-exec (O_CLOEXEC).

(3) The kernel sends SIGPIPE to the writing process, and write() fails with -1 and errno EPIPE. The default action of SIGPIPE terminates the process, so write() never returns unless SIGPIPE is ignored (SIG_IGN) or handled, or the write used send() with MSG_NOSIGNAL. This does not apply to pipes via plain write(). With the signal ignored, write() returns -1 with errno EPIPE. This condition applies when all read ends are closed in all processes, including duplicates. POSIX specifies the same behaviour (SIGPIPE, then EPIPE).
